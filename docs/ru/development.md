# Разработка

Перед предложением изменений прочитайте
[руководство по участию](../../CONTRIBUTING.md). Эта страница описывает особенности
разработки в данном репозитории.

## Структура репозитория

- `src/app` содержит страницы App Router и обработчики HTTP-маршрутов.
- `src/components` содержит интерфейс продукта и переиспользуемые интерфейсные
  примитивы.
- `src/lib/services` отвечает за бизнес-операции и транзакции базы данных.
- `src/lib/access` отвечает за анонимные сессии, членства, приглашения и
  проверки ролей.
- `src/lib/realtime` отвечает за уведомления PostgreSQL и работу SSE.
- `src/lib/ratelimit`, `src/lib/validators` и `src/lib/errors` предоставляют
  общую защиту запросов.
- `prisma/schema.prisma` и `prisma/migrations` определяют схему PostgreSQL и
  историю прямых миграций.
- `scripts` содержит защищённые средства запуска интеграционных тестов,
  эксплуатационные команды и проверки репозитория.
- `e2e` содержит браузерный набор тестов для Chromium.

Предпочтительное направление зависимостей: интерфейс → обработчик маршрута →
сервис → Prisma → PostgreSQL. Серверные компоненты могут вызывать сервисы напрямую.
Сохраняйте инварианты авторизации и конкурентного доступа в сервисах или базе
данных, а не дублируйте их в браузере.

## Настройка

Следуйте варианту разработки из исходного кода в
[Начале работы](getting-started.md):

```bash
npm ci
cp .env.example .env
docker compose up -d postgres
npm run prisma:generate
npm run prisma:deploy
npm run dev
```

Используйте Node.js 22.23.2 и npm 10.9.8. При намеренном изменении зависимостей
файл блокировки и `package.json` должны изменяться вместе.

## Быстрые проверки

Во время работы запускайте проверки, относящиеся к изменению:

```bash
npm run typecheck
npm test
npm run lint
npm run format:check
```

Перед отправкой запроса изменений выполните более широкий набор локальных проверок:

```bash
npm run check:docs
npm run check:repo
npm run security:check
npm run check:licenses
npm run build
npm run check:standalone
```

`npm run audit:dependencies` обращается к сервису рекомендаций npm, поэтому
требует доступа к сети. Изучайте каждую находку; не подавляйте уязвимость высокой
степени опасности только ради успешного завершения команды.

## Тесты базы данных и браузера

Тесты базы данных могут удалять или перезаписывать тестовые данные. Они
пропускаются или отклоняются, пока средство запуска не получит явное
подтверждение, что данные можно удалять. Никогда не используйте эти команды с
рабочей, общей или другой ценной базой данных.

Набор базовых проверок Docker создаёт изолированный проект Compose и временный
том, проверяет миграции, работоспособность, доступ, сохранность при перезапуске
и корректное завершение, а затем удаляет этот проект:

```bash
TEST_DATABASE_IS_DISPOSABLE=1 npm run test:docker
```

Для набора тестов на хосте сначала предоставьте PostgreSQL 16, созданную
специально для тестирования:

```bash
TEST_DATABASE_IS_DISPOSABLE=1 DATABASE_URL='postgresql://...' \
  npm run test:database
```

Обёртка Playwright по умолчанию создаёт и удаляет временную схему:

```bash
TEST_DATABASE_IS_DISPOSABLE=1 DATABASE_URL='postgresql://...' \
  npm run test:e2e
```

Установите Chromium командой `npx playwright install chromium`. Дополнительные
защищённые средства запуска очистки, обновления и базовой проверки доступа перечислены в
`package.json`.

## Изменения схемы

Создавайте миграцию на локальной одноразовой базе разработки:

```bash
npm run prisma:migrate
npm run prisma:generate
```

Закоммитьте новый каталог миграции и связанные изменения кода, который зависит
от схемы. Никогда не редактируйте уже применённую миграцию, чтобы изменить
развёрнутую схему. В запросе изменений опишите преобразования данных, ограничения
совместимости, требования к резервной копии и стратегию отката. В production
существующие миграции применяются через `npm run prisma:deploy`; команды
`migrate dev` и `migrate reset` там не используются.

## Правила кода и интерфейса

- Сохраняйте строгий TypeScript и явно сужайте неизвестные входные значения.
- Перед добавлением новой абстракции или зависимости используйте существующие
  принятые шаблоны валидации, ошибок, сервисов и интерфейса.
- Сохраняйте навигацию с клавиатуры, видимость фокуса, семантический HTML и
  мобильную вёрстку.
- Не отрисовывайте предоставленный пользователем HTML.
- Сохраняйте пользовательские строки приложения на русском, пока в нём не
  появится намеренно спроектированная система локализации.
- Добавляйте тесты для успеха, ошибок авторизации, некорректного ввода и важных
  границ конкурентного доступа.

## Документация и скриншоты

Английские страницы являются источником истины. В одном изменении обновляйте
русский и испанский перевод, не меняя команды, имена переменных и ограничения.
Проверка документации контролирует наличие требуемых страниц, переключатели
языка и локальные ссылки.

Продуктовые скриншоты находятся в `docs/assets`. На них должны быть только
синтетические данные; они не должны показывать URL досок, реквизиты приглашений
или ссылку восстановления владельца, cookie, персональную информацию или
инфраструктуру оператора. Скриншоты создаются защищённым средством запуска
Playwright; перед коммитом проверьте
изображение вручную.

## Зависимости, лицензии и помощь ИИ

Предпочитайте существующие зависимости. При добавлении новой проверьте её
сопровождение, лицензию, транзитивные пакеты и влияние на среду выполнения. При
необходимости обновите `package-lock.json` и уведомления о сторонних
компонентах, затем запустите проверки лицензий и безопасности.

Вклад, созданный с помощью ИИ, приветствуется, но участник по-прежнему обязан
понимать изменение, проверять происхождение и лицензирование, удалять
конфиденциальные данные из промптов и окружения, а также предоставлять те же
результаты тестирования и проверки, что и для написанного вручную кода.
