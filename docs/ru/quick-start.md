# Быстрый старт: установка на сервер с мастером

Это самый простой production-сценарий для тех, кто только знакомится с
самостоятельным хостингом. Установщик спросит домен и адрес электронной почты,
сам создаст все пароли базы и секреты приложения, при необходимости установит
Docker, запустит приложение и настроит автоматический HTTPS через Caddy.

В результате получится установка на одном сервере. Сервер, DNS, резервные
копии, обновления и мониторинг всё равно остаются в вашей зоне ответственности.
Для нестандартных и критичных установок используйте подробные руководства
[Развёртывание](deployment.md), [Конфигурация](configuration.md) и
[Эксплуатация](operations.md).

## Что подготовить заранее

- Новый Linux-сервер с публичным IP-адресом и доступом `root` или `sudo`.
  Установщик умеет автоматически ставить Docker на Debian и Ubuntu. На другом
  дистрибутиве сначала самостоятельно установите Docker Engine с Compose v2 и
  Git.
- Практический минимум — 2 ГБ оперативной памяти и 10 ГБ свободного места. На
  небольшом сервере во время сборки образов может понадобиться swap; по мере
  работы дополнительное место потребуется данным базы, образам, журналам и
  резервным копиям.
- Домен или поддомен под вашим управлением, например `retro.example.com`.
- Адрес электронной почты для уведомлений о TLS-сертификате. Caddy сохранит его
  в закрытой конфигурации и передаст центру сертификации.
- Входящие TCP-порты `80` и `443`, открытые в межсетевом экране или security
  group хостинг-провайдера. По возможности разрешайте SSH только с доверенных
  адресов администраторов.
- Отдельное зашифрованное хранилище для копий базы и секретов. Docker-том на том
  же сервере обеспечивает сохранность при перезапуске, но не является резервной
  копией.

Мастер предназначен для нового сервера. Он не удаляет существующий веб-сервер,
не перезаписывает созданный вручную `.env.production` и не удаляет Docker-тома.

## 1. Направьте домен на сервер

В панели регистратора или DNS-провайдера создайте:

- запись `A` с выбранным именем и публичным IPv4-адресом сервера;
- запись `AAAA` только при наличии рабочего публичного IPv6 и настроенного для
  него межсетевого экрана.

Для первой установки используйте обычную DNS-запись без режима CDN или прокси.
Удалите устаревшие записи `A` и `AAAA` для того же имени. Распространение
изменений DNS может занять время. В итоге следующая команда на сервере должна
показать знакомый вам адрес:

```bash
getent ahosts retro.example.com
```

Во всех примерах заменяйте `retro.example.com` своим доменом. Caddy сможет
получить публичный сертификат, только когда домен будет вести на этот сервер, а
порты `80` и `443` станут доступны извне.

## 2. Скачайте и запустите установщик

Подключитесь к серверу по SSH. Сначала сохраните скрипт в файл, не передавая
удалённую программу напрямую в привилегированную оболочку:

```bash
curl --fail --show-error --location \
  https://raw.githubusercontent.com/Rutboy/badaction/main/deploy/install.sh \
  --output /tmp/badaction-install.sh
sudo bash /tmp/badaction-install.sh
```

Если на новом Debian или Ubuntu нет `curl`, установите его:

```bash
sudo apt-get update
sudo apt-get install -y ca-certificates curl
```

Скрипт запросит:

1. домен без `https://`, порта, пути и завершающего `/`;
2. адрес почты для уведомлений о TLS-сертификате;
3. подтверждение, что показанные DNS-адреса ведут на этот сервер;
4. разрешение установить Docker из официального apt-репозитория Docker, если
   рабочие Docker Engine и Compose v2 ещё отсутствуют.

Придумывать и копировать пароли не нужно. Установщик создаст шесть независимых
256-битных значений: три пароля PostgreSQL и три секрета приложения. Он никогда
не выводит их на экран.

Посмотреть план без изменения сервера можно так:

```bash
bash /tmp/badaction-install.sh \
  --dry-run \
  --domain retro.example.com \
  --email admin@example.com \
  --yes
```

Первая сборка образов может занять несколько минут. После исправления ошибки
установщик можно безопасно запустить повторно: он использует уже созданную
закрытую конфигурацию и не удаляет тома PostgreSQL или Caddy.

## Что именно сделает установщик

По умолчанию скачанный скрипт:

1. клонирует текущую ветку `main` в `/opt/badaction` либо использует репозиторий,
   из которого был запущен;
2. при необходимости устанавливает Git и официальные пакеты Docker Engine на
   Debian или Ubuntu;
3. создаёт `/opt/badaction/.env.production` с правами `600`, сгенерированными
   реквизитами и разными ролями администратора, мигратора и приложения в базе;
4. выбирает свободные loopback-порты для прямых host-привязок приложения и
   PostgreSQL;
5. собирает образы мигратора и приложения без `root`, инициализирует PostgreSQL
   16 и применяет прямые миграции;
6. запускает Caddy на публичных TCP-портах `80` и `443`; Caddy получает и
   продлевает HTTPS-сертификат и проксирует запросы в закрытый сервис приложения;
7. задаёт границу доверия в один встроенный прокси Caddy и отключает сжатие на
   upstream во время потоковой передачи SSE;
8. устанавливает `/usr/local/bin/badaction` для простых повседневных команд.

Публично публикуется только Caddy. Host-порты приложения и PostgreSQL остаются
привязаны к `127.0.0.1`. Том данных Caddy сохраняет сертификаты и закрытые ключи
при замене контейнера.

## 3. Проверьте результат

Запустите встроенную базовую диагностику:

```bash
sudo badaction doctor
```

Команда проверит конфигурацию Compose, покажет контейнеры, опросит закрытый
loopback health endpoint и публичный HTTPS health endpoint. Исправный ответ —
`{"status":"ok"}`.

Откройте `https://retro.example.com` в браузере и выполните одноразовую
функциональную проверку:

1. Убедитесь, что браузер показывает действительный HTTPS-сертификат.
2. Создайте тестовую доску.
3. Откройте приглашение участника в приватном окне браузера.
4. Измените карточку в одном окне и проверьте, что второе обновилось без ручной
   перезагрузки.
5. Проверьте экспорт и удалите тестовую доску из окна владельца.

Не публикуйте URL досок, приглашения, cookie браузера и снимки с реальными
данными команды.

## 4. Защитите установку

До приглашения настоящей команды:

- Сохраните зашифрованную внешнюю копию `.env.production`. Потеря или изменение
  секретов приложения может лишить браузеры доступа и сделать приглашения
  недействительными. Никогда не помещайте этот файл в Git, почту, чат или
  обращение.
- Создайте первую копию базы:

  ```bash
  sudo badaction backup
  ```

  Команда создаст закрытый дамп с временной меткой в
  `/opt/badaction/backups`, проверит, что PostgreSQL читает его каталог, и
  покажет путь. Скопируйте файл в зашифрованное хранилище вне этого сервера.
  Локальная копия тоже погибнет вместе с сервером.

- Настройте регулярные внешние резервные копии, срок их хранения, контроль
  свободного места и пробные восстановления. До хранения production-данных
  изучите раздел [Резервные копии](operations.md#резервные-копии).
- Контролируйте `https://retro.example.com/api/health`, перезапуски контейнеров,
  свободный диск, ёмкость PostgreSQL и ошибки очистки по сроку хранения. Зелёный
  health endpoint сам по себе не подтверждает работу realtime и резервных копий.
- Устанавливайте обновления безопасности ОС и Docker Engine. Не открывайте
  Docker socket и не добавляйте недоверенных пользователей в группу `docker`:
  управление Docker фактически даёт права `root`.

Публикация портов Docker может неожиданно взаимодействовать с host-firewall,
например UFW. Проверяйте доступ и ограничения в межсетевом экране
хостинг-провайдера и прочитайте
[предупреждение Docker](https://docs.docker.com/engine/install/ubuntu/#firewall-limitations),
если на сервере используются собственные правила.

## Повседневные команды

Их можно запускать из любого каталога:

| Задача                                | Команда                     |
| ------------------------------------- | --------------------------- |
| Полная базовая диагностика            | `sudo badaction doctor`     |
| Состояние контейнеров                 | `sudo badaction status`     |
| Последние журналы приложения и прокси | `sudo badaction logs`       |
| Журнал одного сервиса                 | `sudo badaction logs caddy` |
| Проверенный дамп базы                 | `sudo badaction backup`     |
| Корректная остановка всех контейнеров | `sudo badaction stop`       |
| Сборка изменений и запуск стека       | `sudo badaction start`      |
| Перезапуск приложения и прокси        | `sudo badaction restart`    |

В журналах могут быть служебные метаданные. Перед передачей очищайте их и
никогда не публикуйте реквизиты, cookie, фрагменты приглашений, URL восстановления
владельца и содержимое досок.

## Обновления

Отдельных release-веток пока нет; исправления безопасности поступают в текущую
`main`. Не настраивайте автоматический `git pull`. Перед обновлением прочитайте
изменения и миграции, создайте и вынесите проверенную копию базы и запланируйте
окно обслуживания по разделу
[Обновления и прямые миграции](operations.md#обновления-и-прямые-миграции).

После такого ревью базовая последовательность для стандартной установки в
`/opt/badaction` выглядит так:

```bash
cd /opt/badaction
sudo badaction backup
sudo git pull --ff-only
sudo bash deploy/install.sh --yes
sudo badaction doctor
```

Установщик повторно использует прежние секреты и окружение. Домен и email для
TLS он молча менять не станет. Миграции базы выполняются только вперёд; ограничения
совместимости и отката разобраны в подробном руководстве по эксплуатации.

## Если установка не завершилась

Скрипт останавливается на первой неудачной проверке и не удаляет данные. Частые
причины и решения:

- **Домен не разрешается:** исправьте записи `A`/`AAAA`, подождите и повторите
  ту же команду.
- **Порт 80 или 443 занят:** остановите или перенастройте существующий Nginx,
  Apache, Caddy или прокси панели управления. Встроенному Caddy нужны оба
  TCP-порта.
- **Docker установлен, но недоступен:** выполните
  `sudo systemctl status docker`. Установщик не заменяет сломанную или
  конфликтующую контейнерную среду.
- **Публичный HTTPS ещё не готов:** запустите `sudo badaction logs caddy`,
  проверьте DNS и firewall провайдера, подождите минуту и снова выполните
  `sudo badaction doctor`.
- **Контейнер нездоров:** используйте `sudo badaction status` и
  `sudo badaction logs postgres migrate app caddy`.
- **Найден существующий том или проект `badaction-production`:** остановитесь и
  найдите принадлежащие прежней установке окружение и резервные копии. Мастер
  намеренно не подключает новые реквизиты к потенциально ценным данным. Не
  удаляйте том только ради продолжения.
- **Не хватило памяти или диска:** добавьте swap или увеличьте сервер, безопасно
  освободите место и повторите запуск. Не удаляйте неизвестные Docker-тома.

Другие случаи описаны в [Диагностике](troubleshooting.md). Для собственного
прокси, существующего PostgreSQL, нескольких реплик, внешнего registry или
отдельного хранилища секретов используйте расширенное руководство
[Развёртывание](deployment.md), а не слой Caddy для быстрого старта.
