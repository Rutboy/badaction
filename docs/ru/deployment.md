# Развёртывание

Репозиторий предоставляет базовую конфигурацию Docker Compose для одного
Linux-хоста. Она собирает отдельные образы миграций и приложения, запускает
PostgreSQL 16, применяет прямые миграции Prisma и привязывает порты базы данных
и приложения к интерфейсу обратной петли.

Это не готовая управляемая production-платформа. До обслуживания реальных
команд оператор должен предоставить DNS, завершение HTTPS, корректно
настроенный обратный прокси, резервное копирование и проверку восстановления,
мониторинг, управление секретами и защиту хоста и базы. Включённый именованный
том обеспечивает сохранность, но не является резервной копией или схемой
высокой доступности.

## Предварительные требования

- Проверенная ревизия исходного кода Badaction.
- Docker с BuildKit и команда Compose v2 (`docker compose`). Проект не
  устанавливает минимальную версию Docker или Compose.
- Достаточно места на хосте для образов, данных PostgreSQL и отдельных резервных
  копий.
- DNS-имя и обратный прокси, завершающий HTTPS.
- Шесть независимо созданных реквизитов: три пароля ролей PostgreSQL и три
  HMAC-секрета приложения.
- Проверенное место хранения резервных копий и оператор, способный восстановить
  PostgreSQL 16.

Поставляемая цепочка миграций поддерживает PostgreSQL 16 со схемой `public`.
Другие основные версии PostgreSQL и альтернативные схемы не поддерживаются.

## Подготовка окружения

Скопируйте production-шаблон в игнорируемый файл и ограничьте права:

```bash
cp deploy/production.env.example .env.production
chmod 600 .env.production
```

Шесть раз создайте новое значение и храните каждый результат отдельно:

```bash
openssl rand -hex 32
```

Отредактируйте `.env.production` и заполните все пустые поля. В частности:

- `POSTGRES_PASSWORD`, `POSTGRES_MIGRATOR_PASSWORD` и
  `POSTGRES_RUNTIME_PASSWORD` должны различаться и содержать не менее 32
  символов; связанные с ними имена ролей администратора, мигратора и приложения
  также должны быть разными и соответствовать шаблону
  `[a-z_][a-z0-9_]{0,62}`;
- `DOCKER_MIGRATOR_DATABASE_URL` должен использовать роль мигратора, а
  `DOCKER_RUNTIME_DATABASE_URL` — роль приложения. Оба URL используют имя
  Compose-сервиса `postgres`, например
  `postgresql://badaction_app:HEX_PASSWORD@postgres:5432/retro?schema=public`;
- `DOCKER_VISITOR_TOKEN_SECRET`, `DOCKER_BOARD_ACCESS_SECRET` и
  `DOCKER_RATE_LIMIT_KEY_SECRET` должны быть разными, не содержать шаблонных заглушек
  и иметь длину не менее 32 символов;
- `DOCKER_APP_ORIGIN` должен точно совпадать с публичным HTTPS-источником, не
  иметь завершающего `/`, пути, запроса или фрагмента, например
  `https://retro.example.com`.

Пароли в шестнадцатеричной кодировке не требуют URL-кодирования. Если пароль
базы содержит зарезервированные для URL символы, закодируйте их в каждом
затронутом URL базы. Никогда не добавляйте `.env.production` в коммит, не
копируйте его в образ и не печатайте развёрнутую конфигурацию Compose в
публичном журнале.

`COMPOSE_PROJECT_NAME=badaction-production` отделяет этот стек и его именованный
том от локального быстрого запуска. При первом запуске с пустым томом
`deploy/init-production-db.sh` создаёт отдельные роли мигратора и приложения без
прав суперпользователя. Поскольку цепочка миграций выполняет `CREATE SCHEMA IF
NOT EXISTS public`, мигратор получает право `CREATE` на базу, создаёт объекты в
`public` и владеет ими; приложение никогда не должно использовать эту роль.
Роль приложения не может создавать схемы или их объекты. Сценарии инициализации
PostgreSQL не запускаются повторно для существующего тома. Для существующей
установки создайте роли и выдайте права через проверенное изменение базы, затем
обновите два URL. Не меняйте имя проекта и не удаляйте том ради обхода этой
процедуры.

Основной `docker-compose.yml` содержит предсказуемые значения для локальной
разработки. Для общего или публичного экземпляра всегда подключайте
`docker-compose.production.yml`: это переопределение делает URL базы, публичный
источник и реквизиты обязательными.

До сборки проверьте интерполяцию:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  config --quiet
```

`config --quiet` проверяет синтаксис Compose и обязательную интерполяцию.
Проверка среды выполнения всё равно выполняется в приложении: она проверяет
источник, качество секретов, числовые диапазоны и доступность базы. Все
настройки и последствия ротации описаны в
[Конфигурации](configuration.md).

## Сборка и запуск

Соберите оба артефакта из проверенной рабочей копии:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  build migrate app
```

Затем запустите стек и дождитесь успешной проверки работоспособности приложения:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  up --detach --wait --wait-timeout 240
```

Сначала PostgreSQL должна перейти в работоспособное состояние. Затем
одноразовый контейнер `migrate` запускает `prisma migrate deploy`; контейнер
`app` без прав `root` стартует только после успешного завершения миграций.
Проверьте фактическое состояние, не раскрывая значения окружения:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  ps

docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  logs --tail 100 migrate app postgres
```

Журналы всё равно могут содержать эксплуатационные метаданные. Не публикуйте
журналы с содержимым досок, cookie, URL базы, фрагментами приглашений или
ссылками восстановления владельца.

Необязательные настройки `DOCKER_RUNNER_IMAGE` и `DOCKER_MIGRATOR_IMAGE`
выбирают готовые образы. Укажите для обоих артефактов одну проверенную версию
исходного кода и набора миграций, желательно через неизменяемые ссылки по
дайджесту.
Не смешивайте образ приложения и мигратор разных версий. При использовании
готовых образов загрузите и проверьте их по собственному процессу контроля
цепочки поставки и запускайте с `--no-build`, а не пересобирайте под указанной
ссылкой.

## Обратный HTTPS-прокси и SSE

Compose публикует приложение по адресу `127.0.0.1:${APP_PORT}:3000`. Обратный
прокси на том же хосте может направлять публичный HTTPS-трафик на этот адрес
обратной петли. Если прокси работает на другом хосте или в другой сети
контейнеров, базовую конфигурацию нужно явно изменить; не открывайте порт Node.js
напрямую в интернет.

Для всех запросов задайте обычные доверенные заголовки переадресации. Для
маршрута событий доски сохраните потоковую передачу:

- используйте HTTP/1.1 или новее до вышестоящего сервера;
- отключите буферизацию ответа, кеширование, сжатие и преобразования;
- держите соединение с вышестоящим сервером открытым с тайм-аутом чтения больше
  12-секундного интервала служебных сообщений;
- быстро передавайте разрыв соединения, чтобы сервер освобождал ёмкость потока.

Приложение уже возвращает `text/event-stream`,
`Cache-Control: no-store, no-transform`, `Connection: keep-alive` и
`X-Accel-Buffering: no`. Настройка прокси всё равно обязательна. Этот фрагмент
Nginx иллюстрирует нужное поведение; интегрируйте его с политикой TLS и
безопасности оператора:

```nginx
location ~ ^/api/boards/[0-9a-f-]+/events$ {
    proxy_pass http://127.0.0.1:3000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Accept-Encoding "";
    proxy_buffering off;
    proxy_cache off;
    gzip off;
    proxy_read_timeout 60s;
    proxy_send_timeout 60s;
}
```

Клиент также сверяет авторитетное состояние доски каждые 30 секунд, а сервер
повторно проверяет доступ к потоку каждые 30 секунд. Этот резервный механизм
уменьшает влияние временной ошибки SSE, но не делает неисправный прокси или
слушатель допустимым.

`TRUSTED_PROXY_HOPS` определяет только адрес из `X-Forwarded-For`, который можно
использовать для вторичных ограничений злоупотреблений. Оставьте `0`, если
каждый переход на настроенной границе доверия не контролируется и не
документирован. Для прямого пути от Nginx к приложению границей прокси обычно
является `1`; дополнительные балансировщики нагрузки меняют это число. Неверное
положительное значение может довериться адресам атакующего или объединить
несвязанных клиентов.

## Семантика подключения PostgreSQL

В production контейнер мигратора получает `DOCKER_MIGRATOR_DATABASE_URL`, а
долгоживущее приложение — отдельный `DOCKER_RUNTIME_DATABASE_URL`. Внутри
контейнера приложения его `DATABASE_URL` используется для трёх типов доступа:

- пул Prisma для запросов приложения;
- одна постоянная `pg`-сессия на процесс приложения после открытия первого
  потока обновлений — для PostgreSQL `LISTEN`;
- временная `pg`-сессия во время каждой попытки очистки по сроку хранения — для
  удержания рекомендательной блокировки.

Для URL приложения используйте прямое подключение к PostgreSQL или пулер,
сохраняющий привязку к сеансу. Пул только для транзакций несовместим с `LISTEN`
и блокировкой очистки. Успешный ответ `/api/health` не доказывает работу этих
сеансовых возможностей, поскольку маршрут проверки работоспособности выполняет
только короткий `SELECT 1`.

Планируйте число подключений для каждой реплики приложения: у каждой есть
собственные пул Prisma и слушатель обновлений, а очистка ненадолго добавляет ещё
одну сессию. Репозиторий не задаёт универсальный размер пула Prisma, потому что
ёмкость зависит от хоста и базы. До открытия экземпляра протестируйте полный
поток доски с выбранной топологией подключений.

## Проверка развёртывания

Сначала запросите конечную точку обратной петли с хоста:

```bash
curl --fail --show-error --silent http://127.0.0.1:3000/api/health
```

После настройки DNS и TLS запросите публичную конечную точку и проверьте
сертификат:

```bash
curl --fail --show-error --silent https://retro.example.com/api/health
```

Работоспособный ответ имеет вид `{"status":"ok"}`. Он означает, что конфигурация
среды выполнения разобрана, процесс не завершается и проверка базы с предельным
временем 1,5 секунды прошла. Он не проверяет состояние миграций, доставку
обновлений, ход очистки, резервные копии, буферизацию прокси, свободное место или
публичный поток работы с доской.

Выполните одноразовую функциональную проверку через публичный источник:

1. Создайте доску в одном профиле браузера.
2. Погасите приглашение участника в отдельном профиле.
3. Убедитесь, что обновления приходят в оба профиля без ручной перезагрузки.
4. Выполните мутацию и экспорт.
5. Удалите одноразовую доску из профиля владельца.

Не записывайте URL приглашений, cookie или содержимое досок во время проверки.
Наблюдайте за журналами приложения и PostgreSQL и подтвердите появление
записи о событии очистки по сроку хранения.

## Завершение и ограничения развёртывания

Используйте Compose для отправки `SIGTERM` приложению вместо убийства процесса:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  stop app
```

При завершении приложение переводит проверку работоспособности в состояние
`unavailable`, отменяет очистку или дожидается её и закрывает слушатель
PostgreSQL. Внутреннее предельное время жизненного цикла равно 25 секундам,
время подготовки контролирующего процесса — 30 секундам, а Compose оставляет 60
секунд до принудительного завершения. Другому оркестратору дайте не меньше
времени. Повторный сигнал завершения может принудительно остановить процесс.

Включённая настройка — отправная точка для одного хоста. Она не предоставляет
автоматическое переключение при отказе, поэтапные развёртывания, изменение схемы
без простоя,
автоматизацию сертификатов, удалённые резервные копии, централизованные журналы,
метрики, оповещения, ограничения ресурсов или глобальный лимит SSE-соединений.
Несколько реплик могут разделять базу и координировать встроенную очистку, но
умножают число подключений и локальные ограничения потоков; до масштабирования
спроектируйте и проверьте ограничения входящего трафика и последовательность
обновления.

Процедуры резервного копирования, восстановления, прямых миграций, очистки по
сроку хранения, проверки работоспособности и восстановления владельца приведены
в [Эксплуатации](operations.md). При ошибках запуска, базы или обновлений в
реальном времени используйте [Диагностику](troubleshooting.md).
