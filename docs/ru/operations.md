# Эксплуатация

Операторы отвечают за базу данных, секреты, HTTPS-прокси, резервные копии,
мониторинг, последовательность обновлений и инфраструктурные журналы. Файлы
Compose дают базовую конфигурацию для одного хоста, но не предоставляют
управляемую PostgreSQL, высокую доступность, удалённое хранилище резервных копий,
сертификаты или оповещения.

Установка из мастера [Быстрого старта](quick-start.md) поддерживает команды
`sudo badaction doctor`, `status`, `logs`, `backup`, `start`, `stop` и
`restart`. Эта обёртка подключает необязательный Compose-слой Caddy. Явные
команды ниже нужны для понимания и собственной настройки операций.

Команды ниже используют `.env.production` и оба Compose-файла. Выполняйте их из
проверенной рабочей копии репозитория. Никогда не помещайте развёрнутые значения
окружения, cookie посетителей, фрагменты приглашений, ссылки восстановления
владельца или пользовательское содержимое в публичное обращение или журнал.

## Работоспособность и мониторинг

Не требующая аутентификации конечная точка `GET /api/health` возвращает
`Cache-Control: no-store` и один из ответов:

```json
{ "status": "ok" }
```

с HTTP 200 либо:

```json
{ "status": "unavailable" }
```

с HTTP 503. Ответ 200 означает:

- обязательная конфигурация среды выполнения успешно разобрана;
- приложение не находится в состоянии завершения;
- PostgreSQL ответил на `SELECT 1` в пределах 1,5-секундного предельного времени
  приложения.

Ответ не проверяет набор применённых миграций, сеанс `LISTEN` для обновлений в
реальном времени, ход очистки по сроку хранения, потоковую передачу прокси,
свежесть резервной копии, место на диске или полный сценарий работы с доской. Поэтому
проверка может оставаться успешной при ошибочной настройке обновлений или
очистки.

Используйте конечную точку для проверки готовности и дополните её следующими
средствами:

- оповещения о перезапусках контейнеров, загрузке CPU, памяти, файловой системы
  и ёмкости PostgreSQL;
- `prisma migrate status` для нужной базы во время обновлений;
- мониторинг событий очистки и оповещения при частичном или ошибочном результате;
- синтетический поток работы с доской, проверяющий HTTPS, сохранность cookie,
  членство, мутацию, уведомление SSE об изменении и экспорт без сохранения
  реальных реквизитов;
- проверки возраста резервных копий и плановые проверки восстановления.

Начинайте диагностику с узко ограниченных статуса и журналов:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  ps

docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  logs --tail 100 migrate app postgres

curl --fail --show-error --silent https://retro.example.com/api/health
```

Удаляйте конфиденциальные данные из журналов перед передачей. Типовые ошибки
описаны в [Диагностике](troubleshooting.md).

## Резервное копирование

Создавайте резервные копии PostgreSQL независимо от именованного тома Docker.
Том сохраняет данные при замене контейнера, но не защищает от потери хоста,
ошибки оператора, повреждения или разрушительного изменения схемы.

Следующая команда создаёт на хосте логическую резервную копию PostgreSQL в
специальном формате. Изменяйте имя выходного файла в соответствии с вашей
политикой хранения:

```bash
install -d -m 700 backups
umask 077
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  exec -T postgres \
  sh -c 'pg_dump --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" --format=custom --no-owner --no-privileges' \
  > backups/badaction.dump
```

Работающий без остановки базы `pg_dump` транзакционно согласован, но записи,
принятые после его снимка, не попадут в файл. Если такое окно потери недопустимо,
определите стратегию технического обслуживания или непрерывного восстановления.
Для больших экземпляров в дополнение к логическим дампам рассмотрите встроенные
в платформу физические резервные копии и восстановление на момент времени.

Для каждой резервной копии:

1. Отдельно от дампа запишите ревизию исходного кода приложения, основную версию
   PostgreSQL и временную метку UTC.
2. Зашифруйте её, ограничьте доступ и скопируйте за пределы хоста приложения.
3. Убедитесь, что `pg_restore --list` может прочитать файл.
4. Регулярно восстанавливайте её в изолированное окружение PostgreSQL 16 и
   выполняйте проверки приложения.
5. Применяйте политику хранения резервных копий, соответствующую вашим
   обязательствам по приватности.

Резервные копии содержат названия и содержимое досок, отображаемые имена,
голоса, задачи, историю членств и хеши реквизитов. Они могут сохранять данные
после удаления из рабочей базы очисткой по сроку хранения. Защищайте и удаляйте
их как конфиденциальные данные; срок хранения приложения не удаляет независимые
резервные копии или журналы прокси.

Не используйте копию активного каталога данных PostgreSQL на уровне файловой
системы как резервную, если платформа PostgreSQL не предоставляет
документированную процедуру согласованного снимка.

## Проверка восстановления

Проверяйте восстановление вдали от рабочей базы. Используйте PostgreSQL 16 и
пустую базу; никогда не восстанавливайте поверх единственной актуальной копии.

Для локальной проверки скопируйте production-шаблон в отдельный игнорируемый
`.env.restore`. Заполните все пустые значения свежими данными только для теста,
задайте три разные роли и три разных пароля базы, выберите свободные значения
`POSTGRES_PORT` и `APP_PORT` и согласуйте с ними локальный
`DOCKER_APP_ORIGIN`. Явное имя проекта создаёт для проверки отдельный именованный
том. Запустите production-сервис PostgreSQL, чтобы инициализировать ограниченные
роли мигратора и приложения:

```bash
cp deploy/production.env.example .env.restore
# Перед продолжением заполните все пустые поля изолированными тестовыми значениями.
docker compose \
  --env-file .env.restore \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --project-name badaction-restore \
  up --detach --wait postgres
```

Восстановите данные непосредственно в пустую базу `POSTGRES_DB`. Подключитесь под
административной ролью, но используйте `--role`, чтобы восстановленные объекты
принадлежали мигратору, а его права по умолчанию предоставляли роли приложения
доступ к данным:

```bash
docker compose \
  --env-file .env.restore \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --project-name badaction-restore \
  exec -T postgres \
  sh -c 'pg_restore --username "$POSTGRES_USER" --role "$POSTGRES_MIGRATOR_USER" --dbname "$POSTGRES_DB" --exit-on-error --no-owner --no-privileges' \
  < backups/badaction.dump
```

Запустите production-профиль с восстановленной базой:

```bash
docker compose \
  --env-file .env.restore \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --project-name badaction-restore \
  --profile app \
  up --detach --wait --wait-timeout 240
```

Полностью отдельный хост ещё безопаснее. После восстановления:

1. Убедитесь, что одноразовый контейнер миграций успешно завершился. Его обёртка
   применяет прямые миграции и отзывает у роли приложения доступ к
   `_prisma_migrations`.
2. Проверьте работоспособность и число строк, затем создайте новую синтетическую
   доску для проверки членства, обновлений в реальном времени и экспорта.

Свежие HMAC-секреты намеренно не позволяют проверить восстановленные ранее
существовавшие реквизиты сессий или приглашений. Проверка непрерывности
реквизитов требует отдельно контролируемой копии исходных HMAC-секретов и
выделенного тестового реквизита; защищайте такую проверку так же, как рабочую
среду.

Не публикуйте восстановленные пользовательские данные и не используйте в
тестовом экземпляре обычную cookie пользователя из рабочей среды. После записи
результата удалите окружение проверки по утверждённой процедуре удаления данных.

Когда подтверждено, что восстановленные данные можно удалить, удалите
изолированный стек и том:

```bash
docker compose \
  --env-file .env.restore \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --project-name badaction-restore \
  --profile app \
  down --volumes --remove-orphans
```

При реальном восстановлении остановите все процессы записи приложения,
подготовьте чистую целевую PostgreSQL 16 с отдельными ролями администратора,
мигратора и приложения, восстановите выбранную резервную копию от имени роли
мигратора, примените только прямые миграции нужной версии приложения и
изолированно проверьте её до изменения подключения приложения. Сохраняйте
предыдущую базу без изменений и с ограниченным доступом до принятия результата
восстановления.

## Обновления и прямые миграции

Миграции Prisma являются прямыми. Проект не обещает работу старого приложения с
новой схемой или одновременную работу старых и новых процессов записи.
Используйте согласованное окно технического обслуживания, если конкретные
миграции не проверены как безопасные для смешанных версий.

Для базовой конфигурации Compose:

1. Изучите изменения исходного кода и каждую новую SQL-миграцию. Проверьте
   совместимость с PostgreSQL 16, блокировки, преобразования данных, необходимое
   свободное место и длительность на восстановленной копии рабочего объёма.
2. До простоя соберите или получите соответствующую пару образов `migrate` и
   `app`.
3. Создайте и проверьте резервную копию.
4. Остановите все процессы записи приложения.
5. Запустите `prisma migrate deploy` через новый образ мигратора.
6. Запустите новое приложение и проверьте состояние миграций, работоспособность
   и одноразовый сквозной сценарий.

Основные команды Compose:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  build migrate app

docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  stop app

docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  run --rm migrate

docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  up --detach --wait --wait-timeout 240
```

При готовых образах загрузите проверенную пару и пропустите шаг сборки. Обычный
сервис `migrate` может повторно проверить миграции во время `up`;
`migrate deploy` применяет только ожидающие миграции.

Конечная точка работоспособности не подтверждает состояние миграций. Проверьте
код завершения и журналы мигратора и запустите `npm run prisma:status` из
доверенного окружения исходного кода с точным целевым `DATABASE_URL`.

Автоматических обратных миграций нет. Если откат приложения несовместим с
изменённой схемой, восстановите предшествующую обновлению резервную копию в
новую базу и разверните соответствующее старое приложение с ней. Не
редактируйте применённую миграцию, не запускайте `prisma migrate reset`, не
удаляйте схемы и не очищайте таблицы для импровизированного отката ценных
данных.

## Очистка по сроку хранения

При создании каждая доска получает неизменяемую временную метку истечения. После
истечения доска становится недоступной; физическое удаление выполняется во время
прохода очистки и не гарантируется в точную секунду истечения.

Встроенная очистка включена по умолчанию. Каждый процесс приложения выполняет
попытку при запуске, затем через `RETENTION_CLEANUP_INTERVAL_MINUTES`. Несколько
реплик координируются через рекомендательную блокировку PostgreSQL и хранимую в
базе метку минимального интервала, поэтому в нужном интервале работу выполняет
одна встроенная попытка. Каждая попытка использует ограниченные пакеты, а
крупные наборы дочерних записей досок удаляет порциями. Об ошибке одной доски
или одного класса очистки сообщается без отката всей другой независимой работы.

Отслеживайте структурированные события приложения:

- `retention_cleanup_completed`;
- `retention_cleanup_aborted`;
- `retention_cleanup_skipped_advisory_lock`;
- `retention_cleanup_skipped_minimum_interval`.

Считайте условием оповещения непустой `failedSteps`, положительный
`boardDeleteFailures`, повторяющиеся прерывания или отсутствие успешных
запусков. Очистка добавляет временную сессию PostgreSQL для каждой выполняющей
попытку реплики и может создавать нагрузку на базу; настраивайте интервал и
размер пакета по наблюдаемой ёмкости.

Если `RETENTION_CLEANUP_ENABLED=false`, организуйте внешний доверенный
планировщик. Из полной рабочей копии исходного кода с зависимостями и целевым
`DATABASE_URL` ручной проход запускается так:

```bash
DATABASE_URL='postgresql://...' npm run cleanup:expired -- 1000
```

Необязательный аргумент размера пакета должен быть целым от `1` до `10000`.
Команда печатает JSON-результат и завершается с ненулевым кодом при неполном или
ошибочном проходе. Она использует ту же рекомендательную блокировку, но не
применяет минимальный интервал встроенного планировщика, поэтому задавайте
внешнюю частоту осознанно.

Включённый рабочий процесс GitHub Actions — ручной шаблон внешней очистки; по
умолчанию у него нет расписания. Добавляйте расписание только после создания
защищённого окружения `production` с секретом `DATABASE_URL` и настройки
мониторинга пропущенных или ошибочных запусков. Прямой доступ размещённого
средства запуска CI к базе — решение развёртывания, а не требование. Встроенные
и внешние запуски безопасны при конкуренции благодаря рекомендательной
блокировке, но избыточные запуски всё равно расходуют ресурсы.

Никогда не отключайте очистку без заменяющего расписания. Убедитесь, что
резервные копии и инфраструктурные журналы имеют отдельные политики удаления;
очистка рабочей базы не удаляет их копии.

## Корректное завершение

Контролирующий процесс запускает Next.js. При первом `SIGTERM` или `SIGINT` он
перестаёт принимать новый трафик, из-за чего `/api/health` возвращает 503,
просит жизненный цикл приложения остановить очистку, закрывает общий слушатель
PostgreSQL и затем передаёт сигнал серверному процессу.

Жизненный цикл приложения ждёт до 25 секунд. Контролирующий процесс ждёт до 30
секунд подготовки к завершению, а сервис Compose имеет 60-секундный льготный
период. Настройте внешний оркестратор или диспетчер сервисов как минимум на 60
секунд и быстро исключайте завершающийся экземпляр из трафика. Второй сигнал
может принудительно завершить процесс; используйте его только при готовности
прервать работу.

Остановите приложение без удаления данных PostgreSQL:

```bash
docker compose \
  --env-file .env.production \
  -f docker-compose.yml \
  -f docker-compose.production.yml \
  --profile app \
  stop app
```

В автоматизации развёртывания наблюдайте состояние 503 во время завершения и
чистое завершение контейнера. Не считайте принудительную остановку успешным
корректным завершением.

## Несколько реплик

Все реплики должны использовать одну базу, публичный источник и текущие секреты
приложения. Уведомления PostgreSQL поступают постоянному слушателю каждой
реплики, поэтому закреплённые сессии для доставки событий не требуются.
Встроенная очистка координируется рекомендательной блокировкой и меткой интервала
в базе.

Масштабирование всё равно требует явного проектирования:

- каждая реплика добавляет пул Prisma, постоянный слушатель после использования
  обновлений в реальном времени и временные подключения очистки;
- внутрипроцессный лимит потоков SSE локален для реплики, поэтому на входе также
  нужна глобальная политика соединений и запросов;
- все реплики нужно останавливать для миграции, небезопасной для смешанных
  версий;
- включённые Compose-файлы не развёртывают и не балансируют несколько реплик;
- проверка одной реплики может пройти при неисправном слушателе или пути через
  прокси.

До увеличения числа реплик проведите нагрузочный тест запросов, потоков,
переподключений и очистки с реальными прокси и пулером базы данных.

## Восстановление владельца оператором

В Badaction нет восстановления учётной записи. Очистка cookie посетителя в
браузере владельца приводит к потере реквизита, разрешающего его членство. Один
UUID доски не доказывает владение.

Репозиторий содержит узкую операторскую команду для доски без активного
владельца. Используйте её только после независимой проверки заявителя и
разрешения восстановления. Сервис отказывается создавать ссылку восстановления,
пока существует активное членство владельца; строка владельца, связанная с
истёкшей или отозванной анонимной сессией, отзывается во время попытки. Потеря
cookie при всё ещё активной сессии и строке владельца не восстанавливается этой
командой и требует отдельного проверенного решения инцидента.

Запускайте команду из защищённой полной рабочей копии исходного кода с точными
значениями рабочей среды `DATABASE_URL`, `APP_ORIGIN`, `VISITOR_TOKEN_SECRET`,
`BOARD_ACCESS_SECRET` и `RATE_LIMIT_KEY_SECRET`, переданными под именами среды
выполнения:

```bash
npm ci
npm run prisma:generate
npm run access:claim-owner -- <board-uuid>
```

Команда проверяет production-конфигурацию до изменения состояния. Она отзывает
предыдущую незавершённую ссылку восстановления, создаёт одноразовую ссылку со
сроком не более 24 часов или до истечения доски и печатает итоговый URL
`/join#token`. Этот URL является предъявляемым реквизитом доступа.

Не направляйте URL в общие журналы, протоколы команд, заявки, аналитику,
скриншоты или чат. Передайте его вне системы проверенному владельцу, зафиксируйте
только несекретные аудиторские метаданные и подтвердите погашение. Повторный
запуск команды делает предыдущую непогашенную ссылку восстановления
недействительной.

Модель доступа и данных описана в
[Безопасности и приватности](security-and-privacy.md). До изменения реквизитов,
срока хранения, доверия к прокси или настроек базы прочитайте
[Конфигурацию](configuration.md).
