# Диагностика

Начните со статуса контейнеров и узко ограниченных журналов. Не помещайте в
обращение URL базы данных, cookie, фрагменты приглашений, ссылки восстановления
владельца или содержимое карточек.

```bash
docker compose --profile app ps
docker compose --profile app logs migrate app postgres
curl -i http://localhost:3000/api/health
```

## Порт приложения уже занят

Выберите другой порт обратной петли и согласуйте с ним канонический источник:

```bash
APP_PORT=3100 DOCKER_APP_ORIGIN=http://localhost:3100 \
  docker compose --profile app up --build
```

При разработке на хосте одновременно измените `APP_ORIGIN` и порт, переданный
Next.js. Смешивание `localhost` и `127.0.0.1` также создаёт разные области
cookie браузера.

## PostgreSQL не переходит в работоспособное состояние

Проверьте `docker compose logs postgres` и доступность порта хоста. Контейнер
слушает внутренний порт 5432, даже когда `POSTGRES_PORT` меняет порт на хосте.
Контейнеры приложения должны использовать имя сервиса `postgres`, а не
`localhost`.

Существующие именованные тома сохраняют базу, роли и реквизиты, созданные при
первом запуске. Последующее изменение любой настройки `POSTGRES_*` не
перенастраивает существующий кластер PostgreSQL: сценарий
`deploy/init-production-db.sh` выполняется только для пустого тома. Верните
исходные реквизиты либо создайте и настройте отдельные роли администратора,
мигратора и приложения через проверенное изменение базы. Не меняйте
`COMPOSE_PROJECT_NAME` и не удаляйте том, если его содержимое нельзя
безвозвратно удалить или оно не восстановлено в другом месте.

## Контейнер миграций завершается с ошибкой

Изучите `docker compose logs migrate`. Типичные причины: некорректный
`DOCKER_MIGRATOR_DATABASE_URL` (или локальный `DOCKER_DATABASE_URL`),
использование роли приложения вместо роли мигратора, недостаточные права на
схему, сервер не PostgreSQL 16 или прерванное/ручное изменение схемы. Убедитесь,
что имя и пароль роли в URL совпадают с реально созданной ролью, а
зарезервированные символы пароля URL-кодированы. Проверьте состояние миграций в
целевой базе:

```bash
DATABASE_URL='postgresql://...' npm run prisma:status
```

Не редактируйте ранее применённые файлы миграций и не используйте
`prisma migrate reset` для ценных данных. Перед исправлением инцидента с
миграциями создайте резервную копию базы.

### Prisma предупреждает об `onDelete: SetNull`

`prisma validate` выводит предупреждение для связи источника задачи. Применённая
миграция PostgreSQL 16 намеренно использует список столбцов `ON DELETE SET NULL
(source_card_id)`: при удалении она очищает необязательный источник, сохраняя
обязательный `board_id`. Схема Prisma не умеет выражать такую форму ограничения.
Считайте миграцию источником истины и не заменяйте её обычным составным
ограничением `SET NULL`.

## Проверка работоспособности возвращает 503

`GET /api/health` возвращает 503, пока процесс завершается, при некорректной
конфигурации среды выполнения или ошибке короткой проверки базы. Конечная точка
не проверяет версию миграций, слушатель обновлений, планировщик очистки,
резервные копии или поведение внешнего прокси. До многократных перезапусков
проверьте журналы приложения и базы.

## Production-запуск отклоняет конфигурацию

Переопределение для production требует оба URL:
`DOCKER_MIGRATOR_DATABASE_URL` с ролью мигратора и
`DOCKER_RUNTIME_DATABASE_URL` с ограниченной ролью приложения. Имена трёх ролей
и их пароли должны быть попарно различными, а каждый пароль — содержать не менее
32 символов. Зарезервированные символы паролей в URL необходимо кодировать.
Приложению также нужны точный HTTPS-источник в `APP_ORIGIN` и три разных секрета
длиной не менее 32 символов. `APP_ORIGIN` не может содержать путь, запрос,
фрагмент, реквизиты или завершающий `/`. Известные шаблонные секреты разработки
отклоняются. Допустимые диапазоны приведены в
[Конфигурации](configuration.md).

## Мутации возвращают ошибку источника

Источник браузера должен в точности совпадать с `APP_ORIGIN`, включая схему,
имя хоста и порт. Настройте заголовки переадресации на HTTPS-прокси, но не
задавайте `TRUSTED_PROXY_HOPS` больше нуля, если цепочка прокси не контролируется
и её `X-Forwarded-For` нельзя считать доверенным.

## URL доски возвращает «не найдено»

UUID доски — адрес, а не реквизит доступа. В том же браузере должны быть
активная visitor-сессия и членство в доске. Очистка cookie, смена профиля
браузера или имени хоста, выход из доски или удаление участника прекращают
доступ.
Участнику нужно новое приглашение. Доступ владельца нельзя восстановить только
по UUID; используйте операторскую процедуру из [Эксплуатации](operations.md)
лишь после проверки заявителя.

## Ссылка приглашения не работает

Токен приглашения находится после `#` и обрабатывается браузером; фрагмент не
отправляется в HTTP-запросах. Используйте полный URL `/join#token` в том
браузере, которому нужно получить членство. Срок ссылки также мог истечь, она
могла быть отозвана или исчерпать число использований. Никогда не публикуйте URL,
обращаясь за помощью.

## Обновления в реальном времени задерживаются или переподключаются

Клиент переключается на периодическую сверку, поэтому доска продолжает работать
с более медленными обновлениями. Для нормальной работы SSE убедитесь, что прокси:

- отключает буферизацию ответа, кеширование и сжатие для маршрута событий;
- задаёт тайм-аут чтения вышестоящего сервера больше 12-секундного интервала
  служебных сообщений;
- не преобразует ответы `text/event-stream`.

Используемый приложением URL базы должен поддерживать постоянную сессию
PostgreSQL для `LISTEN`. Пул только для транзакций несовместим. Проверка может
оставаться зелёным при неисправности этого пути, поэтому проверьте сетевую
активность браузера и журналы приложения. См. [Развёртывание](deployment.md).

## Браузерные тесты не запускают Chromium

Установите только поддерживаемый этим проектом браузер Playwright:

```bash
npx playwright install chromium
```

На Linux-хостах CI Playwright могут понадобиться документированные системные
зависимости. Проект не заявляет поддержку Firefox или WebKit.

## Автономный образ не проходит проверку лицензий

Соберите его скриптом репозитория, чтобы очистить автономный результат и создать
уведомления о зависимостях:

```bash
npm run build
npm run check:standalone
```

Шаг подготовки также отклоняет файлы окружения в `.next/standalone`.
